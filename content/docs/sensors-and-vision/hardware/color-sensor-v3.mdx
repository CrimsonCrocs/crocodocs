# Read color from an object close to the robot

The REV Color Sensor V3 is a small I²C sensor for **nearby objects**. It measures red, green, blue, and clear-light values and also has an infrared proximity detector. It is not a camera: its useful color range is very short. REV recommends collecting color data within about **2 cm** of the target for the strongest differentiation. Its proximity reading is rough and depends on target reflectivity and lighting; it is not a precise distance sensor.

This lesson will first display the sensor values. Only after you see how your own sensor behaves should you write code that labels an object “red,” “blue,” or something else.

## Step 1: Configure the physical sensor

Connect the sensor to a Hub I²C port. In the Robot Controller configuration, add **REV Color Sensor V3** to that port and name it `color`. Do not select the older “REV Color/Range Sensor” configuration for a V3.

The V3 and REV's 2m Distance Sensor share an I²C address; REV says they cannot share the same I²C bus. Check bus assignments if the Control Hub reports an address conflict.

## Step 2: Map the device in Java

For color readings, ask the FTC SDK for a `NormalizedColorSensor`:

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
private NormalizedColorSensor colorSensor;

@Override
public void init() {
    colorSensor = hardwareMap.get(NormalizedColorSensor.class, "color");
}
```

</Tab>
<Tab value="Kotlin">

```kotlin
private lateinit var colorSensor: NormalizedColorSensor

override fun init() {
    colorSensor = hardwareMap.get(NormalizedColorSensor::class.java, "color")
}
```

</Tab>
</Tabs>

`hardwareMap.get` connects your Java variable to the device with configuration name `color`. If the name or configured device type differs, initialization fails.

You do not need three separate hardware objects just to read three color channels. One normalized sensor object gives you red, green, blue, and alpha/clear-light measurements.

## Step 3: Display measurements before classifying anything

Read a sample and show each channel in telemetry:

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
NormalizedRGBA sample = colorSensor.getNormalizedColors();

telemetry.addData("Red", "%.3f", sample.red);
telemetry.addData("Green", "%.3f", sample.green);
telemetry.addData("Blue", "%.3f", sample.blue);
telemetry.addData("Clear light", "%.3f", sample.alpha);
telemetry.update();
```

</Tab>
<Tab value="Kotlin">

```kotlin
val sample = colorSensor.normalizedColors

telemetry.addData("Red", "%.3f", sample.red)
telemetry.addData("Green", "%.3f", sample.green)
telemetry.addData("Blue", "%.3f", sample.blue)
telemetry.addData("Clear light", "%.3f", sample.alpha)
telemetry.update()
```

</Tab>
</Tabs>

The channels are normalized values, not calibrated physical color coordinates. Hold a matte red, green, blue, white, and black object at the same close distance. Record how the four readings change. Keep the sensor orientation and built-in LED switch in the same state during your tests.

## Step 4: Make a small, measured color rule

A first rule can compare which channel is largest, but that rule is only a starting exercise. It can mislabel white, gray, reflections, or colors that produce similar channel values.

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
String colorGuess = "uncertain";

if (sample.red > sample.green && sample.red > sample.blue) {
    colorGuess = "red-like reading";
} else if (sample.green > sample.red && sample.green > sample.blue) {
    colorGuess = "green-like reading";
} else if (sample.blue > sample.red && sample.blue > sample.green) {
    colorGuess = "blue-like reading";
}

telemetry.addData("Simple channel comparison", colorGuess);
```

</Tab>
<Tab value="Kotlin">

```kotlin
var colorGuess = "uncertain"

if (sample.red > sample.green && sample.red > sample.blue) {
    colorGuess = "red-like reading"
} else if (sample.green > sample.red && sample.green > sample.blue) {
    colorGuess = "green-like reading"
} else if (sample.blue > sample.red && sample.blue > sample.green) {
    colorGuess = "blue-like reading"
}

telemetry.addData("Simple channel comparison", colorGuess)
```

</Tab>
</Tabs>

The labels say “-like reading” on purpose: this is not a reliable general-purpose color classifier. Improve it only after logging samples from the actual game objects, target distance, room lighting, and LED setting. Add thresholds and an “unknown” case for overlapping or dim readings. Never assume thresholds from another robot transfer to yours.

## Optional: use the proximity reading as a nearby/not-nearby hint

If the SDK exposes this configured device as a `DistanceSensor`, you can display its rough proximity estimate:

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
DistanceSensor proximity = hardwareMap.get(DistanceSensor.class, "color");
double estimatedDistanceCm = proximity.getDistance(DistanceUnit.CM);
telemetry.addData("Rough proximity (cm)", "%.1f", estimatedDistanceCm);
```

</Tab>
<Tab value="Kotlin">

```kotlin
val proximity = hardwareMap.get(DistanceSensor::class.java, "color")
val estimatedDistanceCm = proximity.getDistance(DistanceUnit.CM)
telemetry.addData("Rough proximity (cm)", "%.1f", estimatedDistanceCm)
```

</Tab>
</Tabs>

Treat this as a rough proximity cue, not a precision measurement. REV notes that reflectivity affects the result and recommends a separate distance sensor for accurate range. Test the actual object and mounting distance before using a threshold.

## Step 5: Test the rule like a small experiment

1. Place one known object at the sensor's intended distance.
2. Record several readings without moving the robot.
3. Repeat with each object color your robot needs to distinguish.
4. Repeat under the lighting expected on the field.
5. Try a gap, a dark object, and a shiny object. Decide when the program should return “unknown.”
6. Only then connect the classified result to a mechanism or autonomous decision.

This process shows whether the sensor can answer your robot's question at all. The V3's short color range may make a camera or a different sensor a better fit for a farther-away object.

## Troubleshooting

| What happens | What to check |
| --- | --- |
| Hardware map cannot find `color` | Configured name, I²C port, configured device type, and wiring. |
| Readings are similar for every object | Move the target closer, aim the sensor squarely, and check LED state and reflections. |
| Color changes when the object moves slightly | Fix the sensor and target distance; test a larger area of the object. |
| Proximity varies between objects | Reflectivity affects the estimate; use it only as a rough nearby cue. |
| V3 values differ from V1/V2 values | V3 uses a different sensor chip; recalibrate instead of reusing old thresholds. |
