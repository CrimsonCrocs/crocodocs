title: Mechanism design
description: Turn a game task into a tested mechanism with clear motion, load, and transfer requirements.

A mechanism should solve a defined robot task. Before modeling its plates, describe what it must move, where that object starts, where it must finish, and what variation it needs to tolerate.

For example, “transfer from intake to claw” leaves important questions open. Which way is the object facing? What supports it? How far apart can the mechanisms be? How does the robot detect a failed transfer?

## Define the task

Write a few measurable requirements. Use your own targets rather than treating these examples as competition standards.

| Requirement | Example question |
| --- | --- |
| Reach | Which pickup and scoring positions must be reachable? |
| Load | What mass is moved, including the mechanism's own moving parts? |
| Alignment | How far can the object or robot be offset and still succeed? |
| Time | How quickly must a complete operation finish, including recovery? |
| Space | What must remain clear during every allowed movement? |
| Control | What measurements and reference positions will software have? |

Use [Game strategy](/docs/engineering/design/game-strategy) to decide which tasks matter most. A mechanism for a rarely used task should not prevent the robot from performing its main task reliably.

## Compare simple layouts

Sketch two or three ways to produce the required movement. A slide, pivoting arm, and linkage may reach the same point while needing very different space, support, and control.

Count the **degrees of freedom**: the independent motions you need to control. Fewer can simplify a robot, but only if the remaining geometry still handles the required tasks and alignment error. Adding a wrist may be worthwhile when it solves a real placement problem.

Compare each option at its difficult positions. An arm's load changes with its angle. A linkage can approach a poor mechanical advantage near a straightened position. A long slide may become difficult to support even if it reaches the target.

## Prototype the uncertain part

Build a quick test around the question CAD cannot answer. For an intake, that might be roller spacing and object rejection. For a transfer, it might be whether the receiver captures an object after a small offset.

Use scrap, kit parts, or simple prints where they give a meaningful test. Do not spend days detailing a plate before finding out whether its contact geometry works.

Record the geometry, material, speed setting, object condition, and result. Bring useful measured dimensions back into the layout. A successful hand-fed demonstration is only a starting point; test the object as it will actually arrive from the preceding mechanism.

## Agree on interfaces

An **interface** is where two parts of the robot meet. It can be a mounting pattern, a game-piece handoff, an electrical connector, or a software command.

For each mechanism, agree on mounting references, allowable space, input and output object positions, travel limits, sensor locations, and recovery behavior. Include who must be told when one changes.

The [Transfers guide](/docs/engineering/mechanisms/transfers) explains why collecting an object and delivering it predictably are different jobs. [Mechanics and control](/docs/engineering/team/mechanics-and-control) covers the physical details that affect software feedback.

## Review before detailing

Show the layout to someone who did not draw it. Ask them to trace the complete operation, including the return movement. Check motion, support, fastener access, wiring, and assembly order before adding cosmetic detail.

After building, compare the real mechanism with the model. Record play, flex, wear, and changes made by hand. Update the model before making its replacement parts.
