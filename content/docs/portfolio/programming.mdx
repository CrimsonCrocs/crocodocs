Explain what your code helps the robot do and how you know it works. A sensor diagram, a short example, and a useful test result usually tell a reader more than a long list of libraries.

## Control systems

For the Control Award, explain the problem, the control components, and how feedback improves the robot's performance. Show what the robot measures and what it does with that reading. You do not need to print the full source code.

For example:

| Component | Job | How the robot uses it |
| --- | --- | --- |
| Lift encoder and controller | Stop the lift at a chosen height | Compare the measured height with the target and adjust motor power |
| Home switch | Find a known starting position | Detect home and reset the position reference using your homing routine |
| Camera and aiming code | Aim from different positions | Use a valid target reading to adjust aim, and handle a missing target |

Describe the components on your own robot. Say whether they run in autonomous, TeleOp, or both.

## Software choices

Name the libraries you used and credit their authors. Then explain your team's work: setting up hardware, tuning controllers, combining sensor readings, writing recovery code, or comparing approaches.

A state diagram can show the order of actions. A feedback diagram can show how a measurement changes motor output. Explain unfamiliar terms where they appear, and spend most of the space on your robot.

## Autonomous

Draw the route and label the actions along it. Include sensor checks, choices the code can make, and what happens if a move fails. If the routine changes to suit an alliance partner, explain that too.

Count complete successful runs separately from successful individual actions. A robot that follows its route but misses the scoring action has not completed the whole routine. State what counted as a pass, how many attempts you ran, and which robot and software version you tested.

Use the same starting setup when comparing routines. Label a best run as a best run rather than presenting it as typical performance.

## Testing and graphs

Choose a graph that answers a question:

| Question | What to plot or count |
| --- | --- |
| Does the lift stop at the target? | Target and measured position over time, with units |
| How quickly does launcher speed recover? | Speed before and after each shot, with the recovery threshold marked |
| How much does position drift? | Position error along a route, compared with a known reference |
| Does the routine finish reliably? | Complete successful runs out of all attempts, with reasons for failures |

Explain what the result led you to change. Update rate, accuracy, and successful runs measure different things, so label each clearly.

## Failure and recovery

Show what happens when a sensor loses its target, a mechanism jams, or a driver presses the wrong button. Explain how the robot stops or returns to manual control, and how you tested that behavior.

[Blu Cru](/docs/portfolio/case-studies/blu-cru) uses a state diagram to explain its driver cycle and manual overrides. [Seattle Solvers](/docs/portfolio/case-studies/seattle-solvers) shows how its approach to localization changed through the season.

## Driver controls

Explain which actions a driver can start, what the robot checks before continuing, and how the driver cancels an action. If you claim it saves time, compare the same task before and after the change.

For the code itself, see [nonblocking code](/docs/getting-started/nonblocking-code), [PID control](/docs/control-systems/pid-control), and [sensor fusion](/docs/autonomous/sensor-fusion).
