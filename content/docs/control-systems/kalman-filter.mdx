A Kalman filter combines a **prediction** with a **measurement**. It is useful when you have a model of what should happen and a sensor that gives noisy readings. The filter weighs each source according to how uncertain it is.

This page starts with a deliberately small example: estimating a nearly stationary distance. It is not a complete robot-localization filter. A moving robot needs a motion model, correctly timed measurements, and consistent coordinate frames.

## Start with the problem

Imagine the robot is not moving, but a distance sensor reports `50`, `48`, `52`, and `49 cm`. Averaging or filtering can reduce the wobble, but a Kalman filter also keeps track of its uncertainty and can include a prediction model.

For this simple example, assume the distance should stay about the same between readings. That assumption is wrong if the robot or target is moving quickly; then the model must include motion.

## Step 1: Make a prediction

Keep two values:

- `estimate`: the current best distance estimate;
- `P`: how uncertain that estimate is. A larger `P` means less confidence.

For a stationary target, the predicted distance stays the same. Increase uncertainty by a process-noise value `Q`, because the world may have changed a little since the last reading:

```text
predicted estimate = previous estimate
predicted uncertainty = previous uncertainty + Q
```

`Q` is about changes the model does not capture. It is not a magic smoothing strength.

## Step 2: Compare a new sensor reading

Let `z` be the new measurement and `R` describe measurement uncertainty. The Kalman gain decides how far to move the prediction toward that measurement:

```math
K = \frac{P_\text{predicted}}{P_\text{predicted} + R}
```

Then update the estimate:

```math
estimate_\text{new} = estimate_\text{predicted} + K(z - estimate_\text{predicted})
```

If the sensor is noisy (large `R`), `K` is smaller and the estimate stays closer to the prediction. If the prediction is uncertain (large `P`), `K` is larger and the new reading has more influence.

## Step 3: Work one update by hand

Suppose the previous estimate was `50 cm`, its uncertainty was `4`, and this update adds process noise `Q = 1`. The next sensor reading is `54 cm`, with measurement uncertainty `R = 4`.

1. Predicted estimate: `50 cm`.
2. Predicted uncertainty: `4 + 1 = 5`.
3. Kalman gain: `5 / (5 + 4) = 0.56` (approximately).
4. Estimate: `50 + 0.56 × (54 - 50) = 52.24 cm`.

The result moves toward `54 cm` but does not jump all the way there. After the update, uncertainty decreases because the filter has used another measurement.

## Step 4: Test the assumptions before using it

1. Log raw sensor values while the target is still.
2. Estimate how much those readings vary; use that to reason about measurement noise.
3. Move the target slowly and check whether the stationary-target model follows too slowly.
4. If the real system moves, add a motion model instead of just increasing or decreasing a constant until the output looks smooth.
5. Compare raw readings, predicted values, and filtered estimates in telemetry.

Do not claim the filter fixes sensor bias, incorrect units, a loose mount, or a bad model. Correct those problems first.

## Step 5: Put the scalar filter in Java

This small class implements the same predict-and-correct steps for one distance value. `estimate` is measured in centimeters. `uncertainty`, `processNoise`, and `measurementNoise` are variances, so their units are square centimeters. The starting numbers below are examples; estimate them from repeated sensor readings.

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
public final class ScalarKalmanFilter {
    private double estimate;
    private double uncertainty;
    private final double processNoise;
    private final double measurementNoise;
    private boolean initialized;

    public ScalarKalmanFilter(double processNoise, double measurementNoise) {
        this.processNoise = processNoise;
        this.measurementNoise = measurementNoise;
    }

    public double update(double measurement) {
        if (!initialized) {
            estimate = measurement;
            uncertainty = measurementNoise;
            initialized = true;
            return estimate;
        }

        // Predict: this model expects distance to stay nearly constant.
        uncertainty += processNoise;

        // Correct: move the prediction toward the new reading.
        double gain = uncertainty / (uncertainty + measurementNoise);
        estimate += gain * (measurement - estimate);
        uncertainty *= (1.0 - gain);
        return estimate;
    }
}
```

</Tab>

```kotlin
class ScalarKalmanFilter(
    private val processNoise: Double,
    private val measurementNoise: Double
) {
    private var estimate = 0.0
    private var uncertainty = 0.0
    private var initialized = false

    fun update(measurement: Double): Double {
        if (!initialized) {
            estimate = measurement
            uncertainty = measurementNoise
            initialized = true
            return estimate
        }

        // Predict: this model expects distance to stay nearly constant.
        uncertainty += processNoise

        // Correct: move the prediction toward the new reading.
        val gain = uncertainty / (uncertainty + measurementNoise)
        estimate += gain * (measurement - estimate)
        uncertainty *= 1.0 - gain
        return estimate
    }
}
```

</Tab>
</Tabs>

The first valid measurement initializes the estimate. On later calls, `uncertainty += processNoise` says the stationary-distance prediction becomes a little less certain; the gain then decides how much to trust the new reading.

Use it in an OpMode after mapping a distance sensor named `frontDistance`:

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
ScalarKalmanFilter filter = new ScalarKalmanFilter(0.2, 4.0); // Variance examples

while (opModeIsActive()) {
    double rawCm = frontDistance.getDistance(DistanceUnit.CM);
    if (Double.isFinite(rawCm)) {
        double filteredCm = filter.update(rawCm);
        telemetry.addData("Raw (cm)", "%.1f", rawCm);
        telemetry.addData("Filtered (cm)", "%.1f", filteredCm);
    } else {
        telemetry.addLine("Distance reading is invalid");
    }
    telemetry.update();
    idle();
}
```

This is a one-value stationary-target filter, not a moving-robot localization filter. If the measured object moves, increase the model to represent that motion or use a filter designed for the state you are estimating. The filter also does not replace checking whether the sensor reading is in range or physically plausible.

## Why heading needs special handling

Angles wrap around. `179°` and `-179°` are only `2°` apart, but their ordinary numeric average is `0°`. A simple scalar filter can therefore produce a heading on the opposite side of the field. Use an angle-aware method or a localization library that handles wrapped heading values. Also check whether the IMU has been initialized and mounted according to the FTC SDK instructions.

## Using NextFTC's current control module

NextFTC v2's `control` module does include a model-based `KalmanFilter`. Its current API takes a `LinearModel`, state and measurement standard-deviation vectors, and an optional timestep; it exposes separate `predict(inputs)` and `correct(inputs, outputs)` operations. It is not a one-line `posKalman(q, r)` filter.

That API expects a state-space model, so first understand what the state represents and how your measurements map to it. A one-value stationary filter like the Java example above is a better first implementation when you only need to smooth one sensor. Use the current [NextFTC KalmanFilter API reference](https://kdoc.nextftc.dev/control/dev.nextftc.control.filters/-kalman-filter/index.html) and [Control module overview](https://nextftc.dev/control/) for exact types and setup. Confirm the docs match the module version installed in your robot project.

## When should an FTC team use one?

A Kalman filter can be useful when you have a measured noise problem and a model that predicts how the system changes. For a single jittery sensor reading with no motion model, an exponential moving average or median filter may be easier to tune and explain. For robot pose, use a localization system designed for the sensors, timing, and geometry you have.

Learn the simpler [Low-Pass Filter](./lowpass-filter) first, or read [Sensor Fusion](../autonomous/sensor-fusion) for the difference between combining robot measurements and merely smoothing one signal.
