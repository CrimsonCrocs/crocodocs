## What is Mercurial?

Mercurial is a command-based FTC framework from [Dairy Foundation](https://dairy.foundation/). Its command API models actions with lifecycle methods, requirements, and run states; command groups and a scheduler coordinate those actions. The ecosystem also includes libraries such as Core, Util, and Pasteurized, but the modules and setup depend on the release and project template.

## Version and installation

Dairy maintains more than one line of development and publishes Gradle tooling for FTC libraries. This page is a conceptual introduction, not a pinned installation recipe. Use the current [Mercurial documentation](https://docs.dairy.foundation/Mercurial/) and [Dairy FTC plugins and templates](https://github.com/Dairy-Foundation/Plugins) to choose a compatible release and dependency set. Avoid combining v1 examples with the newer `MercurialFTC` artifact or beta APIs without following the corresponding migration guidance.

## Core concepts

- **Commands** describe setup, repeated execution, completion, and cleanup behavior.
- **Requirements** identify resources a command needs so the scheduler can handle conflicting commands.
- **Run states** control when a command may be scheduled, such as initialization or active OpMode.
- **Command groups** combine actions sequentially, in parallel, or conditionally.
- **Subsystems** organize the hardware and behavior owned by a robot mechanism.

The exact method names and command-group APIs are version-sensitive. Use the official language-specific examples for the version in your Gradle project.

## Build a command that runs for one second

The example sets a motor to low power, keeps it there for one second, then writes zero. First map the motor in your OpMode so the command has a real device to control.

### Step 1: Map the motor

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
private DcMotor motor;
private final ElapsedTime timer = new ElapsedTime();
private final Object motorRequirement = new Object();
private Lambda runMotor;

@Override
public void init() {
    motor = hardwareMap.get(DcMotor.class, "testMotor");
    motor.setZeroPowerBehavior(DcMotor.ZeroPowerBehavior.BRAKE);
}
```

</Tab>
<Tab value="Kotlin">

```kotlin
private lateinit var motor: DcMotor
private val timer = ElapsedTime()
private val motorRequirement = Any()
private lateinit var runMotor: Lambda

override fun init() {
    motor = hardwareMap.get(DcMotor::class.java, "testMotor")
    motor.zeroPowerBehavior = DcMotor.ZeroPowerBehavior.BRAKE
}
```

</Tab>
</Tabs>

The hardware name must match Robot Configuration. The requirement is a marker that says which resource this command owns; reuse the same marker for other commands that control this motor.

### Step 2: Describe the command's four jobs

A `Lambda` command has actions for setup, repeated work, a finish condition, and cleanup. This one resets a timer, repeatedly requests 0.15 power, finishes after one second, and always writes zero when it ends:

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
runMotor = new Lambda("Run motor briefly")
    .setInit(timer::reset)
    .setExecute(() -> motor.setPower(0.15))
    .setFinish(() -> timer.seconds() >= 1.0)
    .setEnd(interrupted -> motor.setPower(0.0))
    .setRequirements(motorRequirement);
```

</Tab>
<Tab value="Kotlin">

```kotlin
runMotor = Lambda("Run motor briefly")
    .setInit { timer.reset() }
    .setExecute { motor.power = 0.15 }
    .setFinish { timer.seconds() >= 1.0 }
    .setEnd { _: Boolean -> motor.power = 0.0 }
    .setRequirements(motorRequirement)
```

</Tab>
</Tabs>

`init` runs once when the command starts. `execute` runs repeatedly. `finish` is checked while it runs. `end` runs when it finishes or is interrupted, so it is where this example removes motor power.

### Step 3: Schedule it when the OpMode starts

Attach Mercurial to the OpMode and schedule the command in `start()`. Mercurial's scheduler handles the command lifecycle while the OpMode is active.

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
@Autonomous(name = "Mercurial: Timed Motor Test")
@Mercurial.Attach
public class MercurialMotorTest extends OpMode {
    // Keep the motor, timer, and command fields from Steps 1 and 2.

    @Override
    public void start() {
        runMotor.schedule();
    }

    @Override
    public void loop() {
        telemetry.addData("Elapsed seconds", "%.2f", timer.seconds());
        telemetry.update();
    }
}
```

</Tab>
<Tab value="Kotlin">

```kotlin
@Autonomous(name = "Mercurial: Timed Motor Test")
@Mercurial.Attach
class MercurialMotorTest : OpMode() {
    // Keep the motor, timer, and command fields from Steps 1 and 2.

    override fun start() {
        runMotor.schedule()
    }

    override fun loop() {
        telemetry.addData("Elapsed seconds", "%.2f", timer.seconds())
        telemetry.update()
    }
}
```

</Tab>
</Tabs>

The snippets belong together inside the same OpMode, with the imports from your selected Mercurial release. Test with the mechanism unloaded at low power. Mercurial's v2 FTC bindings are marked beta in the project documentation, so confirm the imports and lifecycle rules against the [current Lambda guide](https://docs.dairy.foundation/Mercurial/commands/lambda) and [FTC usage guide](https://docs.dairy.foundation/Mercurial/usage); older v1 `Command.once(...)` examples use a different API.

## Choosing Mercurial

A command framework can make shared behaviors and autonomous sequences easier to compose, but it adds concepts and dependencies. Compare the framework with your team's experience, the current project template, and the level of support available before adopting it. A small robot can also be programmed directly with FTC SDK OpModes.
