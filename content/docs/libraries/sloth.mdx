## Overview [#what-sloth-does]

Sloth is a Dairy Foundation tool for sending TeamCode changes to an FTC robot through a hot reload workflow. It uses the Sinister runtime and can work with libraries that provide compatible integrations.

Hot reload is useful during development, but it is not equivalent to rebuilding and installing the complete robot app. Its speed depends on the project, network, change, and robot; no fixed upload time is guaranteed.

## Limitations [#important-limits]

The Sloth project documents that hot reload is limited to eligible classes in the TeamCode package. Changes to dependencies, SDK code, or other non-reloaded files need a full install. Some changes may compile but still not take effect correctly when hot reloaded. Follow the current repository instructions and perform a full install whenever a change falls outside the supported hot-reload scope.

<Callout type="warn" title="Do a full install when in doubt">
Do not rely on a hot reload to deploy a new library, SDK, or build configuration. Confirm that the code running on the Control Hub matches the code you intend to test.
</Callout>

## Installation

Checked **14 October 2026**: Sloth and its Load build plugin are both **0.3.2**. Setup depends on whether the project uses a standard FTC Gradle configuration, Dairy's managed plugins, or older Dairy 1.x libraries. The following is the standard-project route; merge it into the existing `TeamCode/build.gradle` rather than replacing that file.

Place the buildscript configuration before the existing plugin/application lines:

```groovy
buildscript {
    repositories {
        mavenCentral()
        google()
        maven { url 'https://repo.dairy.foundation/releases' }
    }
    dependencies {
        classpath 'dev.frozenmilk:Load:0.3.2'
    }
}
```

After the existing plugin application, apply Load and add the runtime dependency:

```groovy
apply plugin: 'dev.frozenmilk.sinister.sloth.load'

repositories {
    maven { url 'https://repo.dairy.foundation/releases' }
}

dependencies {
    implementation 'dev.frozenmilk.sinister:Sloth:0.3.2'
}
```

NextFTC v2's hardware/robot modules already bring in the Sloth runtime. That does not install the **Load plugin** or create its deployment task. Dairy-managed templates have their own plugin/dependency declarations; follow that route consistently. The README's alternate Dairy Core setup is specifically for older Dairy 1.x projects.

## Slothboard

**Slothboard** is Dairy Foundation's maintained FTC Dashboard fork. Its runtime scanning updates `@Config` classes and OpModes when TeamCode is reloaded. The published version checked on 14 October is **0.3.2+0.6.0**; the fork README still contains an older example version.

With the Dairy releases repository configured, replace the ordinary Dashboard dependency with:

```groovy
dependencies {
    implementation 'com.acmerobotics.slothboard:dashboard:0.3.2+0.6.0'
}
```

The Java packages remain `com.acmerobotics.dashboard`, so the [Dashboard telemetry and configuration examples](./ftc-dashboard) use the same API names. The fork and ordinary Dashboard contain overlapping classes. Remove the ordinary direct dependency and check transitive dependencies too.

If the project already uses Road Runner, its Dashboard dependencies can be excluded on the relevant declarations:

```groovy
implementation('com.acmerobotics.roadrunner:ftc:0.1.25') {
    exclude group: 'com.acmerobotics.dashboard'
}
implementation('com.acmerobotics.roadrunner:actions:1.0.1') {
    exclude group: 'com.acmerobotics.dashboard'
}
```

These exclusions do not add Road Runner to a project that does not use it. Confirm the resolved dependency graph before deploying. For a first integration test, expose one harmless `@Config` value, perform a normal install, then reload a small TeamCode change and verify that the configuration and OpMode list update.

## Development workflow

1. Complete the official initial install and confirm the OpMode runs.
2. Make one small change within the documented reload scope.
3. End the OpMode and use the current Sloth deployment task.
4. Confirm the changed behavior on the robot.
5. Use a full install after dependency, SDK, or other non-reloadable changes.

Keep a standard full-install path available and test it before competition. Hot reload is a development convenience, not a substitute for a known-good deploy process.

## Deployment [#deploy-a-teamcode-change]

Deploy TeamCode changes through the Gradle task after adding Load and completing one normal install. Sloth also exposes runtime scanning APIs, but calling those from an OpMode does not replace the deployment task. With the current task configured, the deploy command is:

```powershell
./gradlew.bat :TeamCode:deploySloth
```

On macOS or Linux:

```sh
./gradlew :TeamCode:deploySloth
```

The Control Hub must already be connected to the computer over USB or ADB Wi-Fi. In Android Studio, select the robot project and run the task after ending the active OpMode. A small edit to a class under `org.firstinspires.ftc.teamcode` can then be loaded without installing the full Robot Controller app again.

Before a normal install, remove the remote hot load so it cannot override the installed code. Load 0.3.2 makes Gradle's `installDebug` and `installRelease` tasks depend on `removeSlothRemote`. The documented Android Studio workflow also configures remote removal as a Before launch task. An explicit CLI sequence remains valid:

```sh
./gradlew :TeamCode:removeSlothRemote :TeamCode:installDebug
```

Use a normal `TeamCode` install after changing Gradle files, adding or updating a library, or changing anything outside the hot-reloaded package. The exact plugin setup and task names depend on the Sloth release and project template, so follow the current Sloth README before adding the task to your project.
