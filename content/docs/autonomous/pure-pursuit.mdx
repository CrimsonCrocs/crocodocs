Pure Pursuit is a path-following idea: instead of steering toward the next point right beside the robot, repeatedly choose a point farther ahead on the path and steer toward it. That moving target helps the robot follow a curve smoothly.

This page explains the geometry. It is not a complete drivetrain controller: encoder localization, motor control, path planning, and safety stops still need to be handled. Most FTC teams should learn the idea, then use a maintained library for the robot-specific implementation.

## The parts of the problem

You need two things:

1. A **path**: a sequence of points describing where the robot should go on the field.
2. The robot's estimated **pose**: its field position and heading, usually supplied by odometry or a localization library.

Pure Pursuit uses the pose to choose a point on the path ahead of the robot. That point is the **lookahead point**. Its distance from the robot is the **lookahead distance**.

## Step 1: Look ahead, not behind

At each update, find the part of the path near the robot and look for a point about one lookahead distance ahead. A line segment may cross a circle around the robot between two stored path points, so implementations often calculate the intersection instead of choosing the nearest stored point.

If there is no useful point ahead, the robot may be at the end of the path or its pose estimate may be wrong. Handle that case explicitly; do not steer toward an old point behind the robot.

## Step 2: Express the point relative to the robot

For the steering calculation, describe the lookahead point in robot-centered coordinates:

- `x` is forward from the robot;
- `y` is sideways from the robot (choose a sign convention and keep it consistent).

For a differential-drive robot, the point defines an arc. The curvature needed for that arc is:

```math
\kappa = \frac{2y}{x^2 + y^2}
```

Curvature is signed: with the convention above, a point to one side asks for a turn toward that side. For example, a target at `(10, 5)` gives `κ = 10 / 125 = 0.08` per distance unit. This is a geometry example, not a motor-power setting.

The drivetrain controller turns curvature and a chosen speed into wheel commands. That last step depends on whether the robot is tank, mecanum, or another drive type; Pure Pursuit alone does not define it.

## Step 3: Choose a lookahead distance

Lookahead distance changes how sharply the robot follows the path:

| Lookahead | What you may see |
| --- | --- |
| Too short | Sharp steering changes, jitter, or cutting across noisy pose updates |
| Longer | Smoother turns, but the robot may cut corners |
| Scaled with speed | More distance to react at higher speed, less at low speed |

Begin slowly with one broad curve. Change lookahead a little at a time and watch the robot's actual track against the planned path. There is no value that works for every robot, speed, and field surface.

## Step 4: Test one path at a time

1. Check the localization estimate while the robot is still. Make sure the field axes and heading direction match your path coordinates.
2. Lift the robot and verify that each motor command turns the wheels in the expected direction.
3. Run a short, slow path in a clear practice area with a stop condition in every loop.
4. Compare the planned path, estimated pose, and the robot's physical motion.
5. If the pose estimate is wrong, fix localization first. If the pose is right but the robot steers too sharply or cuts corners, tune lookahead and speed.

Never test a new path at full speed near people or field elements. Keep the robot easy to stop and have a mentor check the test area.

## Step 5: Implement the geometry in small Java methods

The following helper code implements the part Pure Pursuit contributes: find where each path segment crosses a circle around the robot, pick the furthest valid crossing along the path, and calculate curvature. It assumes field coordinates use `+X` forward at heading zero and `+Y` to the robot's left. Keep your odometry and path points in this same convention.

Start with a simple point type and the circle/segment intersection. For a segment from `a` to `b`, parameter `t = 0` is its start and `t = 1` is its end:

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
static final class Point2 {
    final double x;
    final double y;
    Point2(double x, double y) { this.x = x; this.y = y; }
}

static Point2 furthestLookahead(List<Point2> path, double robotX, double robotY,
                                double radius) {
    Point2 result = null;
    double radiusSquared = radius * radius;

    for (int i = 0; i < path.size() - 1; i++) {
        Point2 a = path.get(i);
        Point2 b = path.get(i + 1);
        double dx = b.x - a.x;
        double dy = b.y - a.y;
        double fx = a.x - robotX;
        double fy = a.y - robotY;

        double quadraticA = dx * dx + dy * dy;
        if (quadraticA == 0.0) continue; // Ignore duplicate consecutive points.
        double quadraticB = 2.0 * (fx * dx + fy * dy);
        double quadraticC = fx * fx + fy * fy - radiusSquared;
        double discriminant = quadraticB * quadraticB
            - 4.0 * quadraticA * quadraticC;
        if (discriminant < 0.0) continue; // This segment misses the circle.

        double root = Math.sqrt(discriminant);
        double t1 = (-quadraticB - root) / (2.0 * quadraticA);
        double t2 = (-quadraticB + root) / (2.0 * quadraticA);
        double t = Double.NaN;
        if (t1 >= 0.0 && t1 <= 1.0) t = t1;
        if (t2 >= 0.0 && t2 <= 1.0 && (Double.isNaN(t) || t2 > t)) t = t2;
        if (!Double.isNaN(t)) result = new Point2(a.x + t * dx, a.y + t * dy);
    }
    return result;
}
```

```kotlin
data class Point2(val x: Double, val y: Double)

fun furthestLookahead(path: List<Point2>, robotX: Double, robotY: Double,

    for (i in 0 until path.size - 1) {
        val a = path[i]
        val b = path[i + 1]

        val dy = b.y - a.y
        val fx = a.x - robotX
        val fy = a.y - robotY

        val quadraticA = dx * dx + dy * dy

        val quadraticB = 2.0 * (fx * dx + fy * dy)
```

This checks every segment and remembers the last valid intersection in path order. If it returns `null`, do not reuse an old target: stop or handle the path endpoint explicitly.

Next, rotate that field point into robot coordinates and turn curvature into left/right commands for a **differential drive**:

<Tabs items={['Java', 'Kotlin']}>
<Tab value="Java">

```java
static double[] tankPowers(Point2 lookahead, double robotX, double robotY,
                           double headingRadians, double lookaheadRadius,
                           double trackWidthInches, double maxSpeedInchesPerSecond) {
    double dx = lookahead.x - robotX;
    double dy = lookahead.y - robotY;

    // Robot coordinates: x forward, y left.
    double localX = Math.cos(headingRadians) * dx + Math.sin(headingRadians) * dy;
    double localY = -Math.sin(headingRadians) * dx + Math.cos(headingRadians) * dy;
    double curvature = 2.0 * localY / (lookaheadRadius * lookaheadRadius);

    double speed = 6.0; // Slow example speed; tune for your robot.
    double turnSpeed = speed * curvature * trackWidthInches / 2.0;
    double left = (speed - turnSpeed) / maxSpeedInchesPerSecond;
    double right = (speed + turnSpeed) / maxSpeedInchesPerSecond;
    double largest = Math.max(1.0, Math.max(Math.abs(left), Math.abs(right)));
    return new double[] { left / largest, right / largest };
}
```

</Tab>
<Tab value="Kotlin">

```kotlin
import kotlin.math.abs
import kotlin.math.cos
import kotlin.math.sin

fun tankPowers(lookahead: Point2, robotX: Double, robotY: Double,
               headingRadians: Double, lookaheadRadius: Double,
               trackWidthInches: Double, maxSpeedInchesPerSecond: Double): DoubleArray {
    val dx = lookahead.x - robotX
    val dy = lookahead.y - robotY

    // Robot coordinates: x forward, y left.
    val localX = cos(headingRadians) * dx + sin(headingRadians) * dy
    val localY = -sin(headingRadians) * dx + cos(headingRadians) * dy
    val curvature = 2.0 * localY / (lookaheadRadius * lookaheadRadius)

    val speed = 6.0 // Slow example speed; tune for your robot.
    val turnSpeed = speed * curvature * trackWidthInches / 2.0
    val left = (speed - turnSpeed) / maxSpeedInchesPerSecond
    val right = (speed + turnSpeed) / maxSpeedInchesPerSecond
    val largest = maxOf(1.0, abs(left), abs(right))
    return doubleArrayOf(left / largest, right / largest)
}
```

In the OpMode loop, call `furthestLookahead(...)` with the current localized pose. If a point is returned, call `tankPowers(...)` and send the result to the left and right motor groups. Stop when the robot is within a measured endpoint tolerance; stop immediately if the OpMode is no longer active. This conversion is for tank/differential drive only. Mecanum drive needs a different mapping, and a complete competition implementation also needs path progress tracking, endpoint behavior, timeouts, and a calibrated localizer.

## Common reasons it does not follow the path

- **The pose drifts:** Pure Pursuit cannot fix bad odometry. Calibrate the localization system first.
- **The robot turns the wrong way:** Check the sign convention for heading, sideways position, and curvature.
- **It cuts corners:** Reduce speed or shorten lookahead; also check whether the path itself has sharp turns.
- **It jitters:** Increase lookahead modestly, reduce speed, and check for noisy pose measurements.
- **It never finishes:** Define what “at the end” means and stop the drivetrain when the endpoint condition is met.

## Use a library for the full controller

The geometry is useful for understanding what a path follower is doing, but robust FTC code also needs localization, speed limits, endpoint handling, drivetrain-specific control, and safe stop behavior.
